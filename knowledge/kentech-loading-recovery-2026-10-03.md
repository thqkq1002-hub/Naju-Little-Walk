# KENTECH 로딩 정체 대응 · v86

## 확인 결과

- 사용자 화면은 `건물과 산책로를 불러오고 있습니다`에서 정체되어 있었다. 이 단계는 기존 구현에서 다운로드·압축 해제·GLTF 해석을 한 문구로 표시했다.
- 배포 모델 GET: HTTP 200, 3,821,613바이트, 원본 gzip과 SHA-256 일치. 확인 환경의 다운로드는 약 0.56초였다.
- 원본 GLB 14,747,452바이트, 112개 메시. 압축 해제 약 113ms, Three.js GLTFLoader 해석 약 30ms로 파일 손상은 확인되지 않았다.
- 실제 Vercel 페이지는 점검 환경에서 캠퍼스 표시와 산책 버튼 활성화까지 완료됐다. 사용자의 연결 상태·브라우저 캐시·기기 조건에서 정체된 직접 원인은 재현되지 않았다.
- 기존 다운로드는 네트워크가 정체되어도 시간 제한과 전송량 표시가 없었다. 이번 수정은 확인된 로딩 경로의 복구 공백을 보완한다.

## 수정

- 스트리밍 다운로드의 실제 수신량과 전체 용량을 표시한다. HTTP가 압축을 자동으로 풀어 전체 용량이 달라질 때는 잘못된 백분율을 표시하지 않는다.
- 30초 동안 응답 또는 새 데이터가 없으면 해당 요청과 응답 스트림을 취소하고, 캐시를 재사용하지 않는 요청으로 한 번 재시도한다. 계속 실패하면 기존 오류·복구 화면을 연다.
- 다운로드 / 압축 해제 / 건물 배치 / 화면 정리 단계를 구분한다.
- 준비 화면에서 사용자가 즉시 다시 불러올 수 있도록 버튼을 추가한다. 재시작·장소 이탈 시 이전 다운로드를 취소한다.
- 압축 해제 후 GLB 헤더·버전·전체 길이를 검증하여 불완전한 캐시 파일을 재다운로드한다.
- KENTECH 모델 URL의 캐시 버전을 갱신한다. Blender 모델은 보존한다.

## 배돌이 매몰 수정

- 후속 화면에서 배돌이 발이 포장면 아래에 가려지는 문제가 확인됐다. 기존 배치 Y=0, 내보낸 광장 포장면의 실제 Y≈0.153m였다. 이동 자료에는 v53 포장면 높이가 빠져 있었다.
- 원본 배돌이 GLTF를 리깅 동작별로 확인한 발 최저점은 약 0.000036m로 유지됐다. 캐릭터 형상·리깅 오류는 아니었다.
- `bitgaram-kentech-world.json`에 기존 광장 윤곽과 포장 상단에 맞춘 보행 바닥을 추가하고, 방문자 출발 높이와 배돌이 배치 높이를 0.153m로 맞췄다. 캐릭터 충돌·접지 그림자도 같은 높이를 사용한다.
- 광장 높이는 기존 Blender 모델에서 측정한 값이며 실제 현장의 측량값을 주장하지 않는다. 지형·모델 형상은 변경하지 않았다.
- 재제작 스크립트에도 같은 바닥 기록을 추가해 다음 내보내기에서 이동 자료가 누락되지 않도록 했다.

- 실제 포장면에 아래 방향 광선을 쏘아 배돌이 발·이동 바닥·출발 높이·캐릭터 충돌 높이가 일치하는 회귀 검사를 추가했다.

- 수정 모델을 로컬 브라우저에서 산책 모드로 열어 두 발과 접지 그림자가 포장면 위에 표시되는 것을 확인했다.
